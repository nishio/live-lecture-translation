# 翻訳・要点整理の更新間隔と費用の見積もり

2026-10-05。**翻訳30秒・要点整理60秒は、費用を抑えつつ間隔を短くする設定例である。翻訳15秒も選べる。** 保存済みAudrey実行を基にした30/60の基本試算は約USD 2.34/時間、6時間でUSD 14.04。標準の60秒・120秒設定を同じ方法で試算したUSD 1.30/時間の約1.80倍になる。クラウド翻訳と分析は独立して動く設計に変更したが、新しい並列実行や間隔での実測はまだなく、料金・到着時間・完了を保証するものではない。

音源はCode for Japan公開のAudrey Tang講演。[帰属・CC BY表示](../../samples/audrey-plurality-seoul-2023/README.md#出典と帰属)と、基にした[325.567秒の実行記録](asr-startup-readiness.md)を参照。この調査では保存済みの費用・時刻・件数だけを集計し、新しい録音、認識、API要求は行っていない。

## 何が「順番待ち」になるか

この測定に使った旧実行では、翻訳と要点整理・概念説明が一つのクラウド処理枠を共有し、相手の完了を待っていた。現在の設計は翻訳と分析をそれぞれ1件ずつ同時に実行でき、同じ種類の処理だけは重複して開始しない。原文の認識は別に進み、ローカルのASRとOllamaの共有ロックは維持する。

初回翻訳は標準の60秒間隔を待たず、翻訳可能な原文が用意できた時点で開始する。初回だけは訳の公開または最初の試行の失敗を待ってから自動分析を始める（準備失敗、対象なし、手動分析は例外）。その後の間隔は各処理の開始から数える。15秒単位の蓄積用認識、文末の判定、設定した間隔、再試行、同じ種類の処理がまだ実行中であることによる待ちは残る。表示の3秒速報は翻訳への直接入力ではない。詳しくは[処理構成](../architecture.md#translation-tracks-unfinished-work)を参照。

## 二つの仮定による試算

少量の初回・終了処理を除く翻訳2〜6の5件と、保存結果再利用を除く分析3件を使った。翻訳1件の平均は入力USD 0.0050885＋出力USD 0.0044100、分析1件の平均は入力USD 0.0129235＋出力USD 0.0114900。

**基本試算A**は、1時間あたりに訳す発話量は変わらないとして翻訳の出力費用を一定に保ち、翻訳の入力費用と分析費用を要求頻度に比例させる。入力には毎回の指示や参照文脈が含まれる。翻訳のsystem指示は各回1,750 UTF-8 bytesで、別に応答schemaと原文がある。ただし入力には翻訳対象そのものも含まれ、全入力を頻度比例にするAはその部分まで繰り返す保守的な仮定である。bytesから正確なトークン内訳は求めていない。

**比較試算B**は、一回あたりの入力も出力も現在と同じまま回数だけ増えるとする。小分けになって訳文が減る効果を無視するため、Aより高くなる。A・Bは異なる仮定であり、実費が必ずその間に収まるという上下限ではない。

| 翻訳 / 分析の間隔 | A：1時間 / 6時間 USD | A：60/120比 | B：1時間 / 6時間 USD | B：60/120比 |
| --- | ---: | ---: | ---: | ---: |
| 60秒 / 120秒 | 1.30 / 7.81 | 1.00倍 | 1.30 / 7.81 | 1.00倍 |
| 30秒 / 60秒 | 2.34 / 14.04 | 1.80倍 | 2.60 / 15.63 | 2.00倍 |
| 20秒 / 60秒 | 2.65 / 15.87 | 2.03倍 | 3.17 / 19.05 | 2.44倍 |
| 15秒 / 60秒 | 2.95 / 17.70 | 2.27倍 | 3.74 / 22.47 | 2.88倍 |

Aの式は `翻訳入力平均×3600/翻訳間隔 + 翻訳出力平均×60 + 分析平均×3600/分析間隔`。Bは `翻訳平均×3600/翻訳間隔 + 分析平均×3600/分析間隔`。6時間は各時間費用の6倍。アプリ内保存結果の再利用は見込まず、API側のキャッシュ単価構成は観測時と同じとした。初回・終了の追加要求、再試行、未確定予約、他の用途の支出、開発用AIと電力は加えていない。

単価、要求回数、入力・出力トークン量、キャッシュと再試行が同じなら、並列化してもこの費用計算は同じである。ただし実際の並列化では開始時刻が変わり、入力に選ぶ文脈、保存結果の再利用、実際の要求回数が変わる可能性がある。したがって、新しい並列処理の実費が旧実行と同じとは断定しない。

別の[歴史的な約1時間の実運用](development-handoff.md#partial-live-cost-observation)では、翻訳59要求USD 0.451689、分析30要求USD 0.679490だった。直近30分のUSD 0.630875を時間換算した値はUSD 1.26175、6時間への単純外挿はUSD 7.5705。今回の60/120試算USD 1.30/時間に近いが、同じ条件の追試ではなく、新しい間隔の裏付けでもない。

## 翻訳と分析の所要時間を別々に比べる

上記5件の翻訳生成時間は平均10.094秒・中央値10.085秒・最大13.486秒、分析3件は平均22.185秒・中央値22.290秒・最大24.617秒だった。現在は両者が独立して動くため、`翻訳時間/翻訳間隔` と `分析時間/分析間隔` を別々に計算する。以下は旧実行の所要時間が変わらないと仮定した参考比であり、並列化後の処理枠使用率や待ち時間を測定したものではない。

| 翻訳 / 分析の間隔 | 翻訳：平均時間/間隔 | 分析：平均時間/間隔 | 翻訳：最大時間/間隔 | 分析：最大時間/間隔 |
| --- | ---: | ---: | ---: | ---: |
| 60秒 / 120秒 | 16.8% | 18.5% | 22.5% | 20.5% |
| 30秒 / 60秒 | 33.6% | 37.0% | 45.0% | 41.0% |
| 20秒 / 60秒 | 50.5% | 37.0% | 67.4% | 41.0% |
| 15秒 / 60秒 | 67.3% | 37.0% | 89.9% | 41.0% |

以前の「合計104%だから15秒設定では処理が追いつかない」という説明は、単一の共有枠を仮定したものであり、現在の独立した処理には適用しない。15/60は選択可能である。ただし、表の最大値は少数の旧要求で観測した値にすぎず、並列時の負荷や今後の遅い応答を保証しない。30/60を費用を抑える設定例として示し、15/60との選択は費用と実際の待ち時間を見て行う。認識や文境界の待ちは残るため、15秒に設定するだけで15秒ごとに訳が到着するとは言えない。

この推計は一つの短い講演の少数要求に基づく。話す速さ、文脈量、出力長、ネットワークやモデルの所要時間で変わり、並列実行と新しい間隔での実費・遅延・精度・理解への効果は未測定。JSONの処理間隔を変える操作と、送信許可・日次予算を増やす操作は分け、見積額を自動で許可額にしない。
